## One page, several files

The front end is [`src/web/index.html`](https://github.com/wilsonify/pykaraoke-ng/blob/main/src/web/index.html) —
markup plus links to the stylesheets and scripts that surround it. There is no
framework, no bundler, and no build step: plain files served from `src/web/`.

| File | Role |
|------|------|
| `index.html` | Markup only — the app shell, sections, and the hidden pickers |
| `css/*.css` | Stylesheets, linked in cascade order (tokens → chrome → components → sections → filters → lists → player → library → settings) |
| `src/bridge.py` | The PyScript bridge that publishes `window.pykaraoke_api` |
| `src/app.js` | The app: pure helpers plus the browser wiring |
| `src/helpers.js` | Pure, DOM-free helpers shared by the app module |

The `<head>` also loads the vendored PyScript runtime
(`/_assets/pyscript/core.js`, `core.css`) and a `<py-config>` block points the
interpreter at `/_assets/pyodide/` and installs the engine wheel from
`/_wheel/`. Both asset directories are generated by `src/scripts/build-web.py`
and are git-ignored.

The nine stylesheets — `base`, `layout`, `buttons`, `sections`, `filters`,
`song-list`, `player`, `library`, `settings` — are linked in that order in
`index.html`; a selector may be declared only once across all of them (the
test suite enforces it), so the link order, not specificity fights, is the
cascade.

## DOM structure

The layout is a single vertical column — a fixed header, a scrollable middle,
and a fixed status bar (see the
[ux-slim-sidebar spec](https://github.com/wilsonify/pykaraoke-ng/blob/main/openspec/specs/ux-slim-sidebar/spec.md)).

```text
#app                         flex column, max-width 450px
├── header.app-header        fixed top: title · Add Folder · Settings
├── main.main-column         the only scrollable region
│   ├── details#library-filters   library / rescan
│   ├── section.search-section    #search-input + kind filter fieldset
│   ├── section.results-section   #results-list  (<ul> of <li> song rows)
│   ├── section.player-section    #stage (canvas · #lyrics · video slot)
│   │                             #current-song-title / artist
│   │                             fieldset.player-controls (prev/replay/play/stop/ff/next)
│   │                             #progress-slider · #volume-slider
│   └── section.queue-section     #queue-list   (<ul> of <li> queue rows)
└── footer.status-bar        fixed bottom: status message · engine status

#settings-panel (outside #app)   inline collapsible settings — no modal
#folder-picker                   hidden <input webkitdirectory>
```

The stage holds all three playback surfaces: a `<canvas id="cdg-canvas">` for
CD+G (wrapped in `<figure id="cdg-view">`, which carries the description),
`<div id="lyrics">` for LRC/MIDI lyrics, and a `#video-slot` for MPEG video.
Only one is active at a time.

Where HTML has a native element for a role, the markup uses the element rather
than the role: the live regions (`#library-count`, `#scan-summary`,
`#playback-state`, `#notices`, `#status-message`, `#settings-rescan-note`) are
`<output>`, the format filters and the transport are `<fieldset>`s, the two
song lists are `<ul>`s of `<li>` rows, and the CD+G surface is a `<figure>`.
The keyboard-selected row is marked with `aria-current`, since the rows are
list items rather than listbox options.

## JavaScript ↔ Python boundary

The bridge (`src/web/src/bridge.py`, loaded by the `<script type="py">` tag in
`index.html`) is deliberately tiny. It builds one `pykaraoke.webapp.KaraokeApp`
and publishes a single JSON-friendly dispatcher:

```python
app = KaraokeApp()

def api(name, *args):
    return getattr(app, name)(*[_to_py(a) for a in args])

window.pykaraoke_api = api
```

On the JS side a single `callApi(name, ...args)` wrapper converts PyProxies
back to JS with `toJs()`. Notes from the bridge docstring:

- JS `Uint8Array` arguments arrive as Python `bytes`/`memoryview`.
- JS objects/arrays are converted deeply with `to_py()`.
- Python `None` becomes JS `undefined`.

The full contract is described in the
[engine API reference](../reference/engine-api.md) and the
[web-engine-api spec](https://github.com/wilsonify/pykaraoke-ng/blob/main/openspec/specs/web-engine-api/spec.md).

## State and persistence

A single plain `state` object holds results, the queue, the current song, and
playback clocks. Two `localStorage` keys persist across restarts:

| Key | Contents |
|-----|----------|
| `pykaraoke-ng:state` | The library + settings JSON (`callApi('to_json')`) |
| `pykaraoke-ng:queue` | The queue as song ids |

`restoreState()` and `persist()` are the only writers; the queue is stored by
id so a re-scan does not duplicate entries.

## The tested surface

Everything the module `export`s is pure and unit-tested; the browser wiring
below it only runs when a document exists.

| Export | Purpose |
|--------|---------|
| `formatTime`, `debounce` | Time formatting; input debouncing (150 ms) |
| `escapeHtml`, `songLabel` | Safe rendering and "Title — Artist" labels |
| `CDG_WIDTH`, `CDG_HEIGHT`, `ZOOM_SCALES`, `KIND_BADGE`, `ELRC_EXT` | Constants |
| `companionBaseName`, `companionMember` | Locating companion audio / `.elrc` files |
| `SongQueue` | Ordered queue: `push`, `removeAt`, `move`, `clear`, `next` |
| `PART_IDS`, `partClass`, `partLabel` | Duet part styling and singer chips |
| `buildLyricLines`, `highlightState`, `findSyllableAt` | Lyric grouping and highlighting |
| `noteToFrequency`, `voiceFor`, `computeNoteTimeline` | MIDI note → Web Audio scheduling |
| `writeTileRgba` | Painting a decoded CD+G tile into a canvas `ImageData` |

Internal, browser-only pieces — `wireUi`, `pickFolder`, `playSong`,
`drawCdgUpdate`, and the `MidiSynth` Web Audio class — depend on the DOM or
Web Audio and are not exported.

### Testing the shipped script

The vitest suite imports the real modules from `src/web/src/` (nothing is
generated or copied). Because `document` is undefined outside a browser, only
the pure helpers run and the DOM wiring stays dormant. A wiring-contract suite
in `tests/web/app.test.js` also reads the shipped `index.html` and
`css/*.css` and checks that every element id the app looks up exists, that the
page keeps its accessibility markup, and that no stylesheet selector is
declared twice.

```bash
cd tests/web
npm ci
npm test
```

## Folder access: Tauri or browser

The front end detects the Tauri runtime and picks a different path to the same
engine call:

| Runtime | Picker | Result |
|---------|--------|--------|
| Tauri (`window.__TAURI__.core`) | `pick_folder` + `list_folder` invoke | Flat `{name, path, size}` entries |
| Plain browser | `<input webkitdirectory>` (`#folder-picker`) | The same entry shape from `webkitRelativePath` |

In both cases the entries go to `callApi('scan_files', entries)`. The Web
`File System Access` API cannot re-open a saved folder on restart, which is why
the Tauri shell exists — see the
[architecture overview](overview.md#why-these-boundaries-stay).

## Editing rules

- Keep it framework-free and build-free: plain HTML, CSS and ES modules served
  straight from `src/web/`. Styles belong in `css/`, one topical file per UI
  area, linked from `index.html` in cascade order.
- Never add a front-end dependency.
- Keep `tests/web` green; extractable logic belongs in exported helpers.
- Engine work belongs in `src/pykaraoke` and must stay **stdlib-only** so it
  runs under Pyodide. Work on the engine, not the UI, when the behaviour is
  engine-neutral.
